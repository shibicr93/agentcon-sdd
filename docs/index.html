Act II: The "Vibe Coding" Reality

Five ways AI generates technically correct,
operationally fatal code.

Now the uncomfortable truth: AI can generate technically correct code that is operationally fatal.

1. The Resource Leak

public void handle(Socket sock) {
    try {
        InputStream in = sock.getInputStream();
        // ... processing ...
        // Missing finally block!
    } catch (IOException e) {
        log.error(e);
    }
}
Impact: File descriptor exhaustion → System crash in 4h

The SDD Fix

Rule: RESOURCE_CONTRACT

Enforce try-with-resources for all AutoCloseable types.

try (InputStream in = ...) {
   // Safe by definition
}
It works in tests, fails under load. A missing finally kills the service in 4 hours. SDD fixes it with RESOURCE_CONTRACT: all AutoCloseable types must be try-with-resources.

2. The Crypto Fail

public byte[] encrypt(String data) {
    Cipher c = Cipher.getInstance("AES/CBC/PKCS5Padding");
    // STATIC IV - FATAL VULNERABILITY
    byte[] iv = new byte[16]; // all zeros
    c.init(Cipher.ENCRYPT_MODE, key, new IvParameterSpec(iv));
    return c.doFinal(data.getBytes());
}
Impact: Semantic Security broken. All messages compromised.

The SDD Fix

Rule: CRYPTO_CONTRACT

Forbid new byte[] for IVs. Require SecureRandom.

mandates GCM/AEAD over CBC

A static IV makes encryption useless. SDD’s CRYPTO_CONTRACT forbids new byte[] IVs and mandates AEAD.

3. The Injection

public User login(String u, String p) {
    // VULNERABLE: Direct concatenation
    String sql = "SELECT * FROM users WHERE user='" + u + "'";
    return db.query(sql);
}
Impact: ' OR '1'='1 dumps entire user database.

The SDD Fix

Rule: SECURITY_CONTRACT

Zero tolerance for string concat in SQL. Mandate PreparedStatement.

This is the classic AI bug. SDD’s SECURITY_CONTRACT bans SQL string concatenation, period.

4. The N+1 Disaster

List<Order> orders = repo.findAll();
for (Order o : orders) {
    // Executes 1 query PER ORDER
    User u = userRepo.findById(o.getUserId());
    dtos.add(new OrderDTO(o, u));
}
Impact: 10k users = 10,001 queries. 30s page load.

The SDD Fix

Rule: PERFORMANCE_CONTRACT

Max query budget: 5 per operation.

Detector forces JOIN or batch fetch.

Correct code can still be fatal to latency. PERFORMANCE_CONTRACT enforces a query budget and forces JOIN or batching.

5. The Memory Leak

public class Cache {
    // Unbounded static map
    private static final Map<String,Object> map = new HashMap<>();
    
    public static void put(String k, Object v) {
        map.put(k, v);
    }
}
Impact: OutOfMemoryError after 3 days uptime.

The SDD Fix

Rule: MEMORY_CONTRACT

Static collections must have eviction policies (LRU/TTL).

Static caches feel harmless until they crash prod. MEMORY_CONTRACT requires eviction policies.

Act III: The Three Pillars of SDD

Architecture for the Age of Agents

SDD becomes real when teams operationalize it.

The SDD Triad

1. The Constitution

The "Why" & "How"

Architectural laws that never change. The bounds of permissible code.

2. Contracts

The "What"

Formal schemas (OpenAPI, AsyncAPI) derived from requirements, not code.

3. Guardrails & Gates

The "Validation"

Checkpoints that ensure specifications remain complete, consistent, and implementable.

The three pillars: Constitution (laws), Contracts (interfaces), Guardrails & Gates (validation). Together they prevent drift.
